# 米家 · 电脑版

把米家设备和这台电脑的状态放在一起看 —— 一个本地运行的桌面程序。

- **设备控制**：开关、亮度、色温、模式、温度、风速、档位，红外遥控器
- **电脑监控**：CPU 占用/温度/风扇/内存/磁盘/网络、本机传感器
- **进程管理**：像手机"最近任务"一样看后台程序，标注哪些是系统进程不能结束
- **定时开关**：给设备设定时开关，到点自动执行
- **天气栏**：室外温度、空气质量，放在最上方
- **事件流**：所有操作和状态变化都有记录

> **免责声明**：本项目是**非官方**的第三方客户端，与小米公司及米家官方没有任何隶属或合作关系。
> “米家 / MiHome / Mijia” 名称及相关商标归其权利人所有，本项目仅在描述性意义上使用。
> 项目仅供学习交流与个人使用，使用产生的任何问题由使用者自行承担。
> 所有凭据（登录 token、摄像头凭据、充电器凭据）只存在你自己电脑上，且已被
> `.gitignore` 排除，不会随源码分发。

## 一、怎么跑起来

### 方式 A：双击桌面图标（推荐）

桌面上的 `米家` 图标就是程序本体。已配置开机自启的话开机就会自动打开。

### 方式 B：源码启动

双击项目目录里的 **`启动米家.bat`**。

首次运行会自动建虚拟环境并装依赖（需要联网，约 1–2 分钟），之后就秒开。

### 方式 C：浏览器

后端起来之后，浏览器打开 <http://127.0.0.1:8765> 也能用，功能一样。

## 二、首次使用

1. 打开程序，左下角点「登录」
2. 输入小米账号密码 / 验证码登录
3. 登录态会存在本机（`.mi.token`），以后自动恢复，不用重复登录

> 登录凭证只存在你自己电脑上，程序不会上传到任何第三方。

## 三、界面速览

| 位置 | 内容 |
|---|---|
| 顶部天气栏 | 室外温度、空气质量、体感温度 |
| 左侧导航 | 全部设备 / 房间分组 / 充电器 |
| 设备卡片 | 点一下展开详情面板 |
| 电脑状态区 | CPU、内存、磁盘、网络实时数据 |
| 进程管理 | 后台程序列表 + 内存/CPU 占用 |
| 事件流 | 所有操作的流水记录 |
| 侧栏底部 | 深色模式、刷新、开机自启、退出登录 |

**设备卡片上的小闹钟图标** = 该设备的定时开关。点开可以设定「每天 HH:MM 自动开/关」。

### 卡片上直接能做的事（不用进详情）

- **红外遥控**：卡片上直接列出这台遥控器的按键，点一下就发码。
- **风扇 / 取暖器 / 加湿器**：档位、模式各占一行按钮（`1 档 2 档 3 档 4 档` /
  `直吹风 自然风`），当前的档位和模式是实心的，点一下直接下发。
  按钮从设备 spec 推出来，换型号不用改代码 —— `services/devices.py` 的
  `quick_actions()`。空调温度、灯亮度这种连续量不做成按钮（那样更难按）。
- **摇头 / 摆风**：档位那一行右侧有个胶囊按钮（`↔ 摇头`），按一下就是开/关
  摆风。它是开关不是档位，所以故意做成圆角和档位按钮区分开。属性同样从 spec
  推（`swing_action()`：优先 `horizontal-swing`，没有就用 `vertical-swing`，
  所以空调的上下扫风也有）。
- **设备关着的时候不发光**：状态点、档位/模式的选中态、摇头按钮全部收掉阴影
  和实心色，只留灰字 —— 「上次是 3 档」还是看得见，但不会被误读成正在运行。
  判定在 `cardIsOff()`：只有**明确读到** `on === false` 才算关，状态还没到
  时不熄灯，否则首屏会先暗一下再亮。

### 拖动排序

设备卡片右上角有个**六点手柄**（鼠标移到卡片上才现形，平时不抢视觉）：
拖住它就能调整同一组里的顺序。

- 顺序**按组存**（「可控制」一组、每个房间一组），存在浏览器 localStorage
  （`mi-dev-order-v2`）。跨组拖没用 —— 分组是按在线状态和房间算出来的，不是摆出来的。
- 键盘也行：手柄聚焦后 `Alt+↑/↓`。**双击手柄**恢复该组默认顺序。
- 搜索结果的顺序不给拖（那是筛出来的，存下来会污染真实顺序）。
- 没排过的设备（新加的）接在排过的后面，不会因为拖过一次就被挤到最前面。

### 托盘与后台

- **最小化 = 进托盘**：窗口从任务栏消失，只剩托盘图标（左键呼出，右键菜单）。
- 进托盘时自动做三件事：停掉摄像头转码链（省 200~300MB）、暂停前端全部定时器、
  把整棵进程树的工作集压到最小。**实测整树 569MB → 96MB**。
- 呼出即点即开（<0.1 秒），页面不重载、数据立刻补一轮；挂起前在播的摄像头会自动续播。
- 托盘右键「释放内存」可随时手动压一次；「退出」等价于点窗口 ✕。
- 关掉窗口（✕）仍然是**完全退出**，不是进托盘。

### 窗口变小以后怎么重排

窗口可以随意拖动缩放（最小 1120×720）。仪表盘和侧栏会跟着重排，不是简单缩小：

| 视口宽度 | 仪表盘 | 侧栏 | 设备网格 |
|---|---|---|---|
| ≥1360 | 三列：功率通栏 + 环境/能源 + 本机右列 | 230px 完整 | 每张卡 176px 起，自动增减列 |
| 1080~1360 | 两列：功率通栏，环境/能源并排，本机通栏 | 200px | 同上 |
| 860~1080 | 单列上下堆叠 | 176px | 同上 |
| <860 | 单列 | 58px **只剩图标** | 单列或两列 |

最后一档是给「系统缩放调到 150%/200%」留的余量 —— 窗口物理宽度不变时，
CSS 宽度会按缩放比例缩小（1520 的窗口在 200% 缩放下 CSS 只有 760）。

图表高度用 `clamp(150px, 20vh, 210px)`，窗口变矮时曲线跟着矮一点，
但有上下限：拉到最小也不会被压成一条线，拉到最大也不会拉成一片空白。

### 矮屏**不**做"设备优先"（试过，当天就撤了）

曾经加过 `@media (max-height:1000px)`，把 `#device-grid` 提到仪表盘前面，
想让设备卡进首屏。结果：仪表盘和天气被顶到**页面最底部**，而 125% 缩放下
1186px 的窗口 CSS 高度只有约 950px，几乎天天命中 —— 等于把主要信息流搞反了。
已撤销，恢复原来的顺序（天气 → 功率 → 环境/能源/本机 → 动态 → 设备）。

矮屏只保留一处小改动：动态卡露 4 条（原来 8 条），`evt.js` 里按窗口高度算。
真要让设备进首屏，正确做法是**压缩仪表盘高度**（矮屏把图表折成一行摘要），
而不是改顺序 —— 那需要动 DOM 结构，另开一轮再说。

## 四、摄像头

支持小米摄像头实时画面 + 云台控制 + 画面翻转。

**性能（本机实测：i5-13600KF + RTX 4070 Ti SUPER / 32GB）**

| 场景 | 耗时 |
|---|---|
| 冷启动首次打开（要走小米 P2P 打洞） | **2.5 秒** |
| 关掉页面 2 分钟内再打开 | **0.1 秒**（复用已握手的通道） |
| 拉流时 ffmpeg 内存 / CPU | 192MB / 1.05 核 |

**画面是怎么走的（2026-10-26 改：分工挪了一次）**

```
小米云 P2P ──> go2rtc  camera（HEVC 裸流）
                    │  ffmpeg: #video=h264  ← 转码在这里（720p / NVENC / 1 秒一个关键帧）
                    v
              go2rtc  camera_h264（H264，rtsp://127.0.0.1:8554/camera_h264）
                    │
                    v
              camhls（-c copy，不解码不编码，只切 HLS，1 秒/片）
                    │
                    v
      /camhls/<did>/index.m3u8  ──>  hls.js 播放
```

**为什么把编码挪给 go2rtc**：原来 camhls 自己按 `nvenc → amf → qsv → mf → libx264`
挨个探测编码器，探测失败要拉黑换下一个——那 200 多行换来一整类「只在特定机器
上复现」的故障（qsv 在合成源上通过、接真实流就 MFX 不支持；h264_mf 的 GOP 与
分片错位）。现在编码参数只存在于 `go2rtc.yaml` 的 `ffmpeg.h264` 一处，
camhls 用 `-c copy` 到哪台机器都一个行为。

**为什么还自己切片、不用 go2rtc 自带的 HLS**：一是 go2rtc 的 HTTP API 整个
关着（它没鉴权、`/api/config` 会吐账号 token，开回来等于重新打开 DNS rebinding
的口子）；二是它自带的 HLS 在 GOP 与分片不对齐时会吐 376 字节的空片，hls.js
直接致命错误。camhls 的 `independent_segments` + 1 秒切点就是为这个存在的，
而切点能不能对齐，现在完全取决于 `go2rtc.yaml` 里那个 `-g 20`。

**性能（同一台机器实测，2026-10-26）**

| 项 | 改前（camhls 自己解码+编码） | 改后（go2rtc 转码 + `-c copy` 切片） |
|---|---|---|
| 切片进程内存 | 192~208 MB | **15 MB**（只封装，不解码） |
| 切片进程 CPU | 约 1 核 | **≈0** |
| 转码进程 | 就是上面那个 | 单独一个（go2rtc 的子进程），720p/20fps |
| 冷启动 | 2.5 秒（热通道） | **约 12~16 秒**（冷通道：P2P + 转码进程起 + 等首个关键帧） |
| 换机器 | 要重新探测编码器 | 改 `go2rtc.yaml` 一行（nvenc↔libx264），Python 不动 |

冷启动这条变慢是**结构性**的：多了一个转码进程要先起来并喂出关键帧，才能切片。
热通道（2 分钟内再来）没这个代价。要压回去就开 `preload`（go2rtc 启动即拉流），
代价是摄像头常开、持续占 WiFi。

> 说明：这一版**没有**让总内存大幅下降（转码还是要有一次解码+编码，只是换了个
> 进程）。真正省内存要靠"不解 HEVC 就不转码"，而 WebView2 解不了 HEVC
> （见 `tests/tools/verify_cam_cred.py` 那类探测：本机 `MediaSource.isTypeSupported('hvc1')`
> 为 false），所以先不碰。要压内存，把 `ffmpeg.h264` 里的 `scale=1280:720` 降
> 到 `960:540`、码率降到 `1200k` 最直接。

**改完要重启程序**：`go2rtc.yaml` 是启动时读的，光刷新页面不会重载。

**首次配置**

把 `cam_secret.json.example` 复制成 `cam_secret.json`，填入：

- `xiaomi.user` / `xiaomi.token` —— 米家账号 ID 与登录 token
- `cameras.<DID>.ip` —— 摄像头在局域网里的地址

再把 `cam.json.example` 复制成 `cam.json`，把示例 DID 换成你摄像头自己的设备 ID。
两者都已被 `.gitignore` 排除，**不会进版本库、不会被分享出去**；
`go2rtc/go2rtc.yaml` 里只有 `${MI_*}` 占位符，由 launcher 启动时注入环境变量。

> 仓库里**不含** `go2rtc/` 下的二进制（`go2rtc-tk.exe` / `ffmpeg.exe`，体积原因），
> 需要自行下载放入：go2rtc 用 [AlexxIT/go2rtc](https://github.com/AlexxIT/go2rtc)
> 的 Windows 版（下载后改名为 `go2rtc-tk.exe`），ffmpeg 用任意 Windows 构建
> （如 gyan essentials 版）。不用摄像头功能可以不装，其余功能不受影响。

**出问题先看自检页**

打开 `http://127.0.0.1:8765/api/cam-diag`：会列出 RTSP 端口是否在听、
ffmpeg 路径是否存在、每个会话的编码器 / 分片数 / 重启次数 / ffmpeg 日志尾巴。

## 五、开机自启

侧栏底部 →「开机自启」。开关会写注册表 `HKCU\...\Run`，**只影响当前用户，不需要管理员权限**。

- 连续 3 次启动失败会自动关闭自启，并留下说明（`autostart_fail.log.disabled`），避免开机反复拉起一个起不来的程序拖慢系统
- 修好之后在侧栏重新打开即可

## 六、目录结构

```
├─ launcher.py        桌面外壳（单实例、拉后端、开窗口）

├─ config.py          所有路径/端口/目录常量（换机器换目录不用改源码）
├─ logx.py            统一日志（logs/mihome.log，按天轮转）
├─ creds.py           凭据加密（Windows DPAPI，token / 摄像头密钥）
├─ netproxy.py        "云调用直连"策略（进程内生效，不污染子进程环境）
├─ routes/            HTTP 层：按领域分蓝图，路径与旧版逐字节一致
│   ├─ auth.py  system.py  devices.py  sched.py  live.py  weather.py
│   └─ pc.py  events.py  ext.py  energy.py  cam.py  charger.py

│   ├─ devices.py     设备类型、规格缓存、设备视图、登录

│   ├─ state.py       进程级单例（登录态、摄像头映射）
│   └─ charger.py     充电器蓝牙桥的按需拉起
├─ panel.py           设备型号 → 控件定义

├─ cam_secret.json    摄像头凭据（**不进版本库**，从 .example 复制）
├─ cam.json           摄像头流配置（**不进版本库**，从 .example 复制）
├─ static/            前端（原生 JS/CSS，无构建步骤）
├─ charger/           充电器（BLE）子模块（凭据 device-config.json 同样只在本机）

├─ tools/             辅助工具（前端压缩、配置迁移、打包体积报告）
└─ tests/             回归测试（按领域分目录）
```

### 分层约定

改代码之前值得先知道两条边界，它们让"改设备逻辑不会碰到天气代码"成立：

1. **`services/` 不许 import flask** —— 服务层能被测试脚本直接驱动，
   不依赖请求上下文；反过来 `routes/` 只做"解请求 → 调服务 → 回 JSON"。
2. **路径只从 `config.py` 取，且用属性访问**（`config.TOKEN_PATH`，
   不要 `from config import TOKEN_PATH`）。测试会把它们指到临时目录，
   用 `from ... import` 拿到的是 import 那一刻的字符串副本，改了不生效。

## 七、开发者：跑测试

```bat
.venv\Scripts\python.exe -m pytest tests\ -v      :: 一条命令，默认跳过要开窗口的
.venv\Scripts\python.exe tests\run_all.py         :: 等价的备用入口（不依赖 pytest）
.venv\Scripts\python.exe -m pytest tests\ -v -m gui   :: 连界面 e2e 一起跑
```

再顺手过一遍静态检查（当前全仓 0 问题，可以当 lint 闸门；`pyflakes` 在
`requirements-dev.txt` 里）：

```bat
.venv\Scripts\python.exe -m pyflakes app.py config.py logx.py creds.py netproxy.py ^
    launcher.py camhls.py services routes tools
```

tests/ 下是**脚本式**测试（顶层直接断言、打印 ✓/✗）。`tests/conftest.py` 把它们
包装成 pytest 用例：每个脚本 = 一个用例、在子进程里跑，所以 `-v` 的通过/失败
是真结果，`-k`/`-m` 也能用。会开窗口的（`e2e/ ui/ tray/`）和需要先有实例的
（`perf/`）默认跳过。

| 目录 | 覆盖什么 |
|---|---|
| `tests/cloud/` | 云端韧性：失败归因、AUTH 不重试、熔断半开、token 半截还原；连接池复用/悄悄断开/分流；请求分池与超时取消 |
| `tests/devices/` | 批量属性读取、设备缓存读写与隔离、能力三态、定时开关 |
| `tests/charger/` | 充电器功率汇总、反向代理、失败分类 |
| `tests/launcher/` | 僵尸实例清理（不误杀）、单实例管道、自启注册表、无黑框 |
| `tests/tray/` | 托盘/挂起守卫：ctypes 三铁律、挂起-隐藏-修剪时序、关闭按钮询问 |
| `tests/system/` | 进程分类与保护规则、进程采样（原生快照 vs psutil 兜底、NVML 读数）、打包隐私自检 |
| `tests/e2e/` | 真机端到端（`-m gui` 才跑）：双击自愈、无黑框、托盘入托盘/呼出、退出链路 |
| `tests/ui/` | 响应式守卫：图表容器定高、SVG 绝对定位、断点齐全 |
| `tests/perf/` | 滚动流畅度与空闲开销、流畅度写法守卫（hls 必须懒加载等） |
| `tests/tools/` | **探针脚本，不是测试**：摄像头延迟/分片/画质、内存分项、CDP 截图、停实例等，手动按需运行 |

常用探针：

| 脚本 | 用途 |
|---|---|
| `tests/tools/probe_cam_latency.py` | 量首帧与分片延迟 |

> 却会去掉 assert。细节写在 `米家.spec` 的注释里。

**前端要不要压缩？**

```bat
.venv\Scripts\python.exe tools\build_frontend.py          :: 只报告能省多少
```

## 九、常见问题

**双击图标没反应**

已修。分两种情况，程序都能自己恢复：

| 情况 | 现在的行为 |
|---|---|
| 上次被强杀，互斥量残留 | 找不到窗口就当首次启动，正常拉起 |
| 后端崩了，窗口还挂在桌面上 | 判定为「废窗口」→ 关掉它 → 重起后端 → 重新开界面 |
**窗口后面跟着一个黑色控制台框**

已修。后端和充电桩桥接进程全部用 `pythonw.exe` 启动（无窗口版），
`tests/e2e/test_desktop_e2e.py` 会枚举桌面上可见的控制台窗口做实测校验
（`-m gui` 才跑）。

**界面显示"待确认"**
这是缓存态：程序用上次缓存的设备列表秒开，正在后台重新拉取真实状态。稍等几秒会自动变成实际状态。

**充电器面板说"本机没有蓝牙适配器"**
这不是充电器的问题，是**系统里没有可用的蓝牙适配器**（桥接自己也连不上任何
BLE 设备）。分两种，处理方式完全不同：

- **用户在系统里关了蓝牙 / 开了飞行模式** → 打开开关即可，面板几秒后自己恢复
- **适配器被弹出、USB 枚举失败** → 看设备管理器有没有
  `未知 USB 设备(设备描述符请求失败)`（错误码 43）。有的话开关和重启都**没用**

面板现在会自己读注册表判断是哪种：命中第 2 种时，提示条会直接说
"蓝牙适配器枚举失败（被系统弹出）"并给断电步骤，不用用户自己猜。

第 2 种的恢复顺序（2026-10-25 实测，前两步**全部无效**，别浪费时间）：

| 手段 | 实测结果 |
|---|---|
| 卸载「未知 USB 设备」+ 扫描硬件改动 | ❌ 扫描后又变回错误码 43 |
| 重启蓝牙支持服务 `bthserv` | ❌ 无效 |
| 禁用/启用蓝牙所挂的 USB 3.0 根集线器 | ❌ 无效（设备删了又被枚举成 43） |
| **彻底断电**：关机 → **拔电源线或关插排** → 等 15 秒 → 开机 | ✅ 唯一有效 |

**关键：普通「重启」和「关机后再按开机」都不够。** 关机后主板 5VSB 待机供电仍在
给无线网卡供电，蓝牙芯片拿不到一次真正的上电复位。必须把电源线拔掉（或关掉插排
开关），等电容放干净。

怎么判断是"卡坏了"还是"只是卡死"：看 `Intel(R) Wi-Fi 6 AX101`（同一张 M.2 卡）。
WiFi 状态 OK 就说明卡本身没问题（CNVio2 卡真掉线 WiFi 会一起消失），断电大概率能救回。

**谁干的**：2026-10-25 18:54 本机实测，第三方托盘工具
`外设电量.exe`（`%LOCALAPPDATA%\Programs\PeripheralBattery\`）对蓝牙适配器发了一次
"删除或弹出设备"，系统事件日志 `Kernel-PnP 事件 225` 有完整记录（带 PID 和设备实例路径）。
弹出后 M.2 内置卡没有"重新插入"这回事，所以卡死在枚举阶段。**装这类外设工具的注意
禁用其开机自启**，它刷新电量时可能再次触发。

面板会区分三种失败原因，别混着猜：

| 面板提示 | 真实原因 | 该怎么办 |
|---|---|---|
| 蓝牙适配器枚举失败（红条） | 被弹出，错误码 43 | **拔电源线断电**，重启无效 |
| 本机没有蓝牙适配器（红条） | 蓝牙开关关了 / 没硬件 | 打开系统蓝牙开关；重连**不会**自己好，所以文案写"复查" |
| 找不到充电器（黄条） | 不在范围 / 被手机米家占着 | 靠近、通电、关掉手机 App 的蓝牙连接 |
| 连接已中断（黄条） | Token 不对、链路抖动 | 看 `charger/charger.log` 的 `last_error` 原文 |

**充电器页面能打开、数据也在跳，但点场景/开关没反应，日志报 405**

看日志里是不是这句话：`场景切换失败: 405 Method Not Allowed: The method is not
allowed for the requested URL.`。**这不是蓝牙问题，也不是桥接问题。**

充电器页面挂在 `/charger/*` 下面，由一个统一的代理转发给本地桥接。
`/charger/<path:sub>` 这条路由必须显式写 `methods=["GET","POST"]`——
Flask 默认只放行 GET，于是页面能打开、读数正常，唯独所有**写操作**
（场景切换 / 接口开关 / 定时 / 屏显）被路由层直接 405 挡掉，函数都进不去。

改完 `app.py` **必须重启程序**才生效（改前端是刷新即可，改后端不是）。
`tests/charger/test_charger_proxy.py` 专门钉这个坑：方法保真、body 保真、
GET 不被修坏。自己加新代理路由时也记得把 methods 写全。

**主页面的「当前总功率」包含充电器吗**

包含。充电器是蓝牙直连的，不在米家设备表里，所以后端 `/api/live` 会额外给一个
`charger_w`（各端口功率之和）。主页面把它算进总数，设备列表里会多一行
「充电器」，副标题标注「含充电器」。

两个细节是刻意的：

- **功率 ≤ 0.5W 或桥接没在跑时，这一行不出现**——宁可没有，也不给你一个假的 0W
- **不为了这个数字去拉起蓝牙连接**。所以刚开机、还没打开过充电器页面时，
  总功率里暂时不含充电器；打开一次之后桥接会活着，就持续有了。
  想让它一直显示（代价是蓝牙连接常驻），把这个限制去掉即可

**场景切换 / 开关点下去没反应，要等一两秒才变**

那是旧实现的遗留：`onSceneClick` 等蓝牙 ACK + Result 回来才更新界面，
而一次往返要几百毫秒到几秒。现在改成**先改界面、失败回滚**（和端口开关一致），
点下去立刻就有反馈。如果看到「场景切换失败」并回滚，那才是真的没成功。

**定时开关到点没执行**
定时**只认正点那一分钟**，错过不补执行（白天突然亮灯比不亮更烦人）。网络失败时会在 5 分钟内重试最多 3 次。

**端口被占用**
后端用 8765，摄像头用 8554/1984。`停止.bat` 会一键清理所有相关进程。

**怎么看日志**
`logs\mihome.log`（统一出口，按天轮转、留 7 天）、`go2rtc/go2rtc.log`（转码）、
`start.log`（后端进程的 stdout/stderr 原始输出，只在排查启动即崩时有用）。
级别用 `MIHOME_LOG_LEVEL=DEBUG` 临时调低，重启生效。

> 以前是 `print` + `log_err()` + `launcher.log` 三套并存，排查一个问题要同时翻
> 三个文件还不知道哪条是哪条。现在只有 `logs/mihome.log` 一个出口，
> 每条都带模块名（`[mihome.cam]` 这种）。

## 十、安全说明

- 后端只监听 `127.0.0.1`，不对外网开放
- 所有写接口校验 `Origin`/`Referer` 同源，且严格比对**协议 + 主机 + 端口**三项
- 静态资源带 `Cross-Origin-Resource-Policy: same-origin`
- 外部传感器推数是唯一放行的写接口，用独立密钥鉴权
- **凭据在磁盘上是加密的**：`.mi.token` / `cam_secret.json` 用 Windows DPAPI
  （密钥由"当前用户 + 当前机器"派生，程序里没有可被拷走的密钥文件）。
  文件首行 `MIHOME1:` 开头的就是密文。
  代价：把目录拷到另一台电脑上，登录态解不开，需要重新登录一次 —— 这是加密
  该有的样子。旧明文文件照样能读，下次写入时自动转成密文。
  排障时想临时用明文：`MIHOME_CRED_PLAIN=1`。
- **云调用直连不改全局环境**：只在进程内替换 urllib 的 opener（`netproxy.py`），
  不再设 `NO_PROXY=*`。子进程（go2rtc / ffmpeg / 充电器桥）的代理配置原样保留，
  天气这类该走系统代理的仍走系统代理。要关掉：`MIHOME_CLOUD_DIRECT=0`。
- **清理僵尸实例的边界**：只认「命令行点名了 `launcher.py` / `app.py` / `米家.exe`
  **且该文件就在本程序目录内**」的进程；窗口按标题找到后还要复核归属进程，
  确认是自己人 才动手。后端正在跑时一个都不碰，绝不误杀别的程序
  （曾经用"命令行含 launcher.py 子串"匹配，误伤过别的项目的同名脚本，已改）

## 十一、性能与内存

这版专门压过一次内存。主窗口 + 后端 + 转码常驻的实测分项（摄像头开着、
1520×960 逻辑窗口 / 125% 缩放）：

| 进程 | 私有内存 | 干什么用的 |
|---|---|---|
| `msedgewebview2`（合 5 个） | 约 280 MB | 界面渲染。离不开了，Chromium 自己就要这么多 |
| `ffmpeg` | 约 208 MB | 摄像头转码（**原来是 448 MB**，见下） |
| 后端 `pythonw` | 约 60 MB | Flask + 小米云会话 + 系统采样 |
| `go2rtc` | 约 56 MB | 把摄像头 P2P 流取下来转成 RTSP |
| 窗口外壳 | 约 70 MB | pywebview / pythonnet 的运行时 |

### 这次改了什么

**摄像头解码走显卡**（省最多的那条）。摄像头是 2304×1296 的 HEVC，原来靠 CPU
软解，一帧原始画面就是 4.5 MB，参考帧队列加起来吃 448 MB。改成 D3D11 硬解
（帧留在显存，只把 720p 成品下载回内存）后降到 208 MB，**首片时间一点没变**。
两个坑写在 `camhls.py` 的注释里：光加 `-hwaccel` 不够，还得声明
`-hwaccel_output_format` 并 `hwdownload`；硬解时反而不能再给 `-pix_fmt yuv420p`。

**界面不再常驻重特效**。登录页那两团光晕原来是 `filter:blur(84px)`（全图卷积，
只能落在合成线程），换成径向渐变；滚动时吸顶的标题栏原来用 `backdrop-filter`
每帧重模糊一遍整行，改成不透明底 + 一条分线。视觉上几乎看不出差别，滚动立刻跟手。

**没人看的时候不干活**。窗口最小化或切到别的应用时，本机面板（2 秒一次）、
设备轮询（20 秒一次）、充电器角标全部跳过，切回来立刻补一次。

**长列表不再全量重排**。进程面板 200 多行两千多个节点，用
`content-visibility:auto` 让视口外的行跳过布局和绘制；设备卡加
`contain:layout paint style`，悬停抬起的阴影不会波及整页。

**后端线程池 16 → 8**。单用户本地应用，并发请求全来自同一个页面，
16 个常驻线程里 12 个是白占。

**云端请求压成一批**（第二批，2026-10-25）。原来每台在线设备单独发一次
`miot_get_props`，11 台就是 11 个往返。但米家云 `/miotspec/prop/get` 的 `params`
本身就是数组，miservice 只是把它封成了单设备。现在 `_batch_read()` 直接发原始数组
（15 台/批），整轮只剩 **1 个请求**，回包按 `(did, siid, piid)` 三元组回填。
想知道一轮到底发了几次请求：`GET /api/status` 的 `batch` 字段里写着。

**轮询分两档**。以前 20 秒一刀切：开关跟不上（别处改了状态屏幕上不来），
温湿度又白读。现在 4 秒只读开关（一次请求十几条参数），45 秒读一次全量读数
（温度/湿度/电量/功率/模式）。开关跟随 20 秒 → 4 秒。
另外加了防重入：上一轮没回来就不再发下一轮，避免弱网下请求堆积。

**首屏后交还工作集**。启动 90 秒后调一次 `SetProcessWorkingSetSize(-1,-1)`，
后端工作集 77.4 MB → 29.7 MB。**说明性质**：私有内存不变（59→60 MB），
这是把暂时不用的物理页换到页面文件的账面优化，下次用到按需换回。

### 第三批：把三个结构性隐患一次性拆掉（2026-10-25 晚）

前两批解决的是"占多少"和"跑多顺"，这三条解决的是"会不会莫名其妙坏掉"。

**单实例改用命名管道**（`launcher.py`）。旧做法是"枚举同名窗口 + 发 WM_CLOSE"
去判断有没有实例在跑，这个方案在本项目翻车过三次：

1. `FindWindowW` 只返回**任意一个**同名窗口 —— 实测认错过 pid，差点把无关窗口关掉；
2. 窗口过程已经死了（webview 崩了但窗口没销毁）时，消息发进去没人处理，
   `PostMessage` 照样返回成功，调用方完全看不出来；
3. 单向消息没有返回值，只能"等 1 秒看窗口还在不在"来猜。

现在改成一个按程序目录 hash 的命名管道（`multiprocessing.connection` 的 `AF_PIPE`）。
后启动的实例先发一条 `show`，拿到的是**真实结果**：

| 回复 | 含义 | 新实例的动作 |
|---|---|---|
| `shown` | 窗口已提到前台 | 立刻退出（实测 **0.2 秒**） |
| `starting` | 后端在跑，窗口还没建好 | 等它，最多 6 秒，不叠实例 |
| `dead` | **后端不通**（窗口在不在都一样） | 接管：清僵尸 → 完整启动 |

`dead` 那条的判定顺序是关键：**先查后端，再看窗口**。废实例的典型特征恰恰是
"窗口还挂着、后端已经死了"，先看窗口就会把死界面叫到前面，用户看到的就是
"双击没反应"。

顺带解决了两件事：

- Windows 内核对命名管道做引用计数，进程死了管道自动消失 —— **没有 stale lock**。
  参考项目用 `QLockFile` 得写一段"判 pid 清残留"的代码，这里不需要。
- 管道名按 `find_dir()` 算，所以**双击 exe 和跑 `启动米家.bat` 认的是同一个实例**，
  不会各开一份。

**请求分池，用户操作不再排队**（`app.py`）。原来所有云端调用共享一个扁平队列，
弱网下点一下开关要等十几秒 —— "按了没反应"比"慢一点"伤人得多。现在两个池子：

- **control 池**（3 个 worker）：开关、云台、设备详情、登录。永远有空位。
- **data/idle 池**（2 个 worker）：界面轮询和后台预取，内部再按优先级排。

为什么不只做优先级：worker 一旦被长轮询占住，control 排到队首也只能干等。
（参考项目是单队列 + 优先级，并发打满时同样要等。）另外任务进队时带**截止时间**，
排队途中已过期的直接扔掉 —— 弱网下积压的轮询数据本来也没人要看。

**开关能力改成三态**（`app.py` / `devcache.py`）。这是本轮唯一一个"真 bug 风险"：

```
网络抖动 → 某台设备的 miot_spec 没拉到 → 不知道它有没有 on 属性
        → 以前当成"确认没有" → 写进 devices_cache.json
        → 下次启动直接读缓存渲染 → 那台设备的开关永久消失，重启也不回来
```

因为缓存只在"没有缓存"时才走在线加载，错的快照不会自愈。现在：

- `_has_on()` 返回 `True / False / **None**`，`None` 专指"规范没拉到，现在不知道"；
- `find_on_iid()` 在规范缺失时**不把兜底值 (2,1) 记住**（否则规范后来拉到了
  也不会重算，之后每次点开关都发到错误属性上，比落盘错误更隐蔽）；
- 只要有一台是 `None`，`_save_dev_cache()` **整份不写**，保留上一份好快照；
- 界面上仍按设备类型猜一个（不然 spec 没到的设备连开关都不给，看着像坏了），
  但这份猜测贴了 `_on_guess` 标签，不许落盘；
- `CACHE_VERSION` 1 → 2，把可能被污染的旧快照整份作废。

### 第四批：把"每秒 41 次重排"降到 2 次（2026-10-25 深夜）

现象是"用起来不跟手"，但不报错、不掉设备、不看指标根本不知道哪坏了。
量出来才看到根子：**空闲（什么都不做）时，全页每秒 41 次布局 + 41 次样式重算**。
主线程被每 23ms 唤醒一次，用户任何时候滚一下、点一下，都可能正好撞上一次重排。

归因方法（比猜快得多）：在真实窗口里 `clearInterval` 逐个停用 12 个定时器，
每停一个量 2 秒布局次数。**停掉本机状态那个 2 秒轮询后，布局直接从 36.8/秒 掉到 0**
—— 其余 11 个定时器都不是主因。然后用 `Profiler` 采样确认 JS 只占 0.06%，
说明时间全花在浏览器内部（布局/样式），不是算法慢。

三处写法各自的问题：

| 写法 | 为什么贵 | 改成 |
|---|---|---|
| 每核条 `style.height = x%` + `transition: height .4s` | height 不是合成属性，0.4 秒过渡 = 每帧重排一次，20~32 个条一起 | `transform: scaleY()`，走合成器，零布局 |
| 进度条 `style.width = x%` + `transition: width` | 同上 | `transform: scaleX()` |
| 每 2 秒 `innerHTML` 重建 tile / 内存行 / 进程行 / 底栏 | 销毁+新建+重新布局，而里面的数只变了几位 | 结构建一次，数值用签名比对后局部更新 |
| 每轮都 `style.setProperty("--pc-c", 颜色)` | 这个变量被一大票元素 `var()` 引用，改一次 = 整棵子树样式重算 | 值没变就不写 |

顺带两件体感问题：

- **入场动画改成只播首次**。以前 `animation` 写死在 `.device-card` 上，于是每次
  切房间/搜索/刷新重建网格，整批卡片都会"从头一个个淡入"（13 台 = 13×18ms 错峰）。
  这是"点了房间之后半天才摆好"的真正原因。现在限定在 `body.booting` 下，
  首屏播完就摘掉这个类。实测切房间 **4~5ms、零动画残留**。
- **hls.min.js 从首屏移走**。它有 414KB，不开摄像头时一行都用不上，却挂在
  `<head>` 里同步加载。现在 `ensureHls()` 按需插 `<script>`，并发调用复用同一个
  Promise。实测摄像头冷启动第 8 秒出画面 1280×720，没变慢。

实测（真实 WebView2 窗口，CDP `Performance.getMetrics`）：

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 空闲布局 | 41 次/秒 | **1.5~2.3 次/秒** |
| 空闲样式重算 | 41 次/秒 | 9~15 次/秒 |
| 空闲主线程占用 | 5.3% | **0.8~1.0%** |
| 切房间（13 张卡重建） | 4ms + 234ms 错峰淡入 | **4ms，无动画** |
| 首屏 JS 解析量 | 含 414KB hls | 少 414KB |

`tests\perf\test_perf_regression.py`（31 项）把这些写法钉住了：谁把 `height` 动画、
整块 `innerHTML`、首屏同步 hls 改回去，测试会直接失败。

### 第五批：窗口缩小后"图形崩了"（2026-10-25 深夜）

现象：把窗口拖小，仪表盘的卡片越拖越长，环境曲线和能源柱状图被拉成一片扁的。

**根因是一个正反馈循环，不是"窄屏没适配"**：

```
draw() 拿 wrap.clientHeight 当 viewBox 高度
  → SVG 是流内元素、height:100%；父容器 height:auto 时百分比失效
  → SVG 退回"按 viewBox 比例算自己的固有高度" = 把高度又算回容器
  → 容器变高 → ResizeObserver 回调 → draw() 读到更大的高度 → …
```

实测后果：1520 宽下 `.dash` 行高 **2293px**，环境卡/能源卡各 **2294px**，
SVG 自己 883 高（正屏 923），曲线挤在最底部一小条 —— 用户看到的就是"崩了"。

三个环节同时切断才治得住：

| 位置 | 原来 | 改成 | 为什么 |
|---|---|---|---|
| `#env-section .cv-chart-wrap` | `height:auto; flex:1 1 auto` | `height:clamp(150px,20vh,210px); flex:0 0 auto` | 高度必须是确定值，flex:1 在没有基准高度时没有意义 |
| `#cv-chart` / `#en-chart` | 流内元素 `height:100%` | `position:absolute; inset:0` | 脱离文档流，永远不会反过来改容器尺寸 |
| `draw()` 的 H | 直接用 `clientHeight` | `Math.min(clientHeight, 480/420)` | 第二道闸：以后有人改回 flex:1 也不会再失控 |

`ResizeObserver` 也补了"尺寸真变了才重画"（亚像素阈值）：没有这道判断，
它和 draw 会互相触发，控制台一直刷
`ResizeObserver loop completed with undelivered notifications`。

顺带修的两处：
- `.grid` 别写 `minmax(min(176px,100%),1fr)` —— WebView2 里这条会让
  `auto-fill` 算不出列数，整条规则失效退成单列（实测 1520 宽也只有 1 列）。
- 主题按钮的图标是 JS 注入的 svg，`ICONS` 里没有 `width/height` 属性，
  一直渲染成 0×0 —— 补了 `#theme-ico svg{width:15px;height:15px}`。
  不补的话，极窄档（只显示图标）那个按钮就是一片空白。

实测（真实 WebView2 窗口，CDP 量 viewBox 与渲染尺寸是否 1:1）：

| 视口宽 | 布局 | dash 高 | 侧栏 | 图表 |
|---|---|---|---|---|
| 2560 | 三列 | 629 | 230 | 1:1 |
| 1520 | 三列 | 629 | 230 | 1:1 |
| 1360~1080 | 两列 | 1058~1073 | 200/176 | 1:1 |
| 1106（最小） | 两列 | 1058 | 200 | 1:1 |
| 1013~760 | 单列 | 1406 | 176/58 | 1:1 |

拖拽压力测试（1520→1120→1520 来回 10 次，含改高度）：**0 次异常**，
`overflowX` 始终 0。`tests\ui\test_responsive.py`（41 项）把这些写法钉住。

### 第六批：托盘 + 后台挂起（2026-10-25 深夜）

最小化入托盘时做三件事：`MiHomeSuspend(true)` 从源头掐掉所有定时器（suspend.js
包裹 `setInterval`，新模块自动被管住）并停摄像头转码链；`EmptyWorkingSet` 把
launcher + 后端 + WebView2 + go2rtc/ffmpeg 整棵树的工作集压进备用列表。
实测 **569MB → 96MB**，呼出 <0.1 秒（页面不重载）。

排查"呼出应答 25 秒超时"用两招：环境变量调低 `_slow_log` 阈值全量打点 +
`_stack_watchdog` 在无进展 12 秒后转储全部线程栈。真凶两个，都已修：
① pythonnet 的 `IntPtr` 不吃 `int()`，必须 `ToInt64()`，否则 show_main 返回
None 白白掉进 EnumWindows 老路；② 对"隐藏+最小化"组合态的窗口，
pywebview 的 `restore()+show()` 不生效（呼出来还是最小化），要用 Win32
`ShowWindow(hwnd, SW_RESTORE)` 一步处理。另一个坑：EnumWindows 回调里
`GetWindowTextLengthW` 对同进程窗口是 SendMessage，属主线程不泵消息就
**永久阻塞** —— 所以 show_main 拿到 hwnd 后直接走 Win32，不再枚举。

### 第七批：把"待机 11% CPU"打到 1%（2026-10-26）

起因是量了一下空闲状态：一个什么都不做的桌面程序，吃了 **11.4% 的单核**。
`py-spy` 采样 110 次，105 次落在同一处 —— `pcsys._top_procs()`。

**根因一：进程榜用 psutil 逐个问。** 取 CPU 时间和内存是"一个进程一次
`OpenProcess`"，264 个进程跑一轮 296ms，每 3 秒一次，等于常年 10% 的单核。
真正要命的不是这个数字，是这 296ms **全程握着 GIL** —— Flask 的请求线程
只能排队。实测 `/api/status` 中位数 0.9ms、**P99 却是 149ms**，用户感受到的
就是"偶尔顿一下"。

改成任务管理器用的那套：`NtQuerySystemInformation(SystemProcessInformation)`
一次调用返回全量链表，进程名、用户态/核心态时间、工作集全在里面。
**296ms → 1.4ms（快 108 倍）**，263 个进程逐一和 psutil 比对，数值零误差。
附带好处是不走 `OpenProcess`，系统进程也能读到，不会因为拒绝访问丢行。
结构体只定义到 `WorkingSetSize` 为止（这段布局从 Win7 到 Win11 没变过），
万一哪天对不上就返回 `None` 退回 psutil 老路 —— `tests/system/test_pcsys_procs.py`
守着这三件事：数值对、速度快一个数量级、退化时不返回空。

**根因二：LHM 探测在白等超时。** CPU 温度要读 LibreHardwareMonitor，它会
先发一个 `urlopen(timeout=2.5)`。机器上没开 Web Server 时（最常见的情况）
**实打实等满 2.08 秒**才失败，每 15 秒一次，启动时那 3 秒也主要是它。
改成先对本机 8085 做一次 0.12 秒的 `connect_ex`，没在监听就立刻返回。
**2083ms → 2.4ms**。顺带加了退避：连续探不到就 5 分钟才试一次，装上 LHM
之后最多等 5 分钟自动恢复，不用重启程序。

**根因三：GPU 靠 `nvidia-smi` 子进程。** 每次查询要起一个进程（53ms），
2 秒一轮就是 2.6% 的单核，任务管理器里还一闪一闪。机器上装了 N 卡就有
`nvml.dll` —— `nvidia-smi` 自己也是调它。改成 ctypes 直连常驻调用，
**53ms → 0.13ms（快 440 倍）**，读数完全一致。没有 `nvml.dll`（A 卡/没驱动）
时自动退回子进程那条路。

**顺带两处启动路径的浪费：**
- `start_app` 用固定 `sleep(0.4)` 轮询端口，后端实测 272ms 就起来了，却要
  等到下一轮才发现 → 改成前密后疏（头 10 次 40ms 一次），省 100~400ms。
- `clear_webview_cache()` 每次启动都删 `Code Cache`，等于每次让 V8 把所有
  js 重新解析编译（实测冷首屏 198ms、热首屏 48ms，差的就是这块）。页面的
  静态资源本来就带 `?v=<mtime>`，旧文件会被当新 URL 重新拉，不需要靠
  "每次清缓存"兜底 → 改成按 `static/` 指纹清：前端改了才清，没改就留着。

同机同刻 A/B（你的实例跑旧代码、另起一个跑新代码，两个进程都在真跑）：

| 指标 | 旧 | 新 |
|---|---|---|
| 空闲 CPU | 11.4% | **1.2%**（-89%） |
| `/api/status` 中位 / P95 | 1.0 / 1.5 ms | 1.0 / 1.5 ms |
| 私有内存 | 50.6 MB | 49.0 MB |
| 首次 `_tick`（冷启动） | 3061 ms | 399 ms |

前端这边就没有优化空间了，量过：DOM 1037 个节点、JS 堆 3 MB、滚动
**75 fps 且 0 次掉帧**、空闲 8 秒 **0 个长任务**。页面本身热启动 48ms 就能
出第一张设备卡 —— 打开时的等待主要在 Chromium 建进程和解释器冷启动，
那部分不是能靠改代码消掉的。


### 第八批：指示灯误关整台设备 + 前端加固（2026-10-27）

**症状**：详情页里把「指示灯」关掉，整台风扇卡片跟着显示"已关闭"，详情面板

## 十二、云端链路的韧性（netguard.py）

`app.call()` 管两件事：**别等太久**（超时）和**别留下僵尸协程**（真取消）。
这一层补另外三件：**抖一下就失败**、**挂了还硬撞**、**坏了看不出来**。

### 原来的四个真实故障模式

| 现象 | 根因 | 现在 |
|---|---|---|
| 设备偶尔集体变灰几十秒 | 一轮批量读只打一次，任何一次抖动整轮抛错 | 单批失败只丢那一批，其余设备照常显示；全失败才抛 |
| 断网时界面比断网前更卡 | 每 4 秒一轮都去撞 25 秒超时，8 个 waitress 线程被占满 | 连续 4 次网络/超时失败开熔断，20 秒内快速失败，冷却后放一个探针 |
| "莫名其妙又要重新登录" | miservice 遇到认证异常会**删掉** `.mi.token`；而备份是 `copyfile` 无条件覆盖，半截文件会把好副本冲掉 | 备份前先校验 JSON；主文件半截时自动从副本原子还原 |
| 其实登录早失效了，界面只是不刷新 | 后台采集线程 `except: pass`，错误被吞掉 | 失败记账；认到 AUTH 就在后台自愈一次，救不回来才提示重新登录 |

### 三条边界（都是刻意的）

1. **写操作的重试是挑过的**：`set_prop` 幂等，允许重试一次；`action`（切换、云台、场景）
   **一次都不重打** —— 重发一次"切换"就是切两次，宁可报错让用户再点。
2. **AUTH 不重试、也不推动熔断**。登录失效时重试和熔断都只会让用户没法重新登录。
3. **认不出来的错误不重试**（`unknown`）。miservice 抛的全是裸字符串异常，
   宁可少打一次云端，也不要在不确定的情况下重复发请求。

### 怎么看它现在什么状态

`GET /api/status` 里多了两个字段：

```json
"health":  {"state": "ok|degraded|down", "consecutive_fail": 0,
            "last_kind": null, "last_error": null,
            "by_kind": {"net": 0, "timeout": 0}},
"breaker": {"open": false, "retry_after": 0.0}
```

`state` 的分级是"连续失败 1~2 次 = degraded，3 次以上 = down"。
界面上"设备不刷新"有三种完全不同的原因（断网 / 米家云抖 / 登录失效），
看这两个字段能直接分开，不用猜。

**侧栏左下角有一个小圆点**（在「浅色模式」上面），把 `conn` 直接摊开：
绿 = 云端已连接，黄 = 网络不稳或这一屏是旧数据，红 = 连不上，灰 = 未登录。
它跟着 4 秒那档轮询一起刷新，不额外发请求；极窄档（58px 图标条）只留圆点。
鼠标悬停有更具体的说明（含"这一屏是缓存的上一轮数据"）。

自愈的日志前缀是 `[self-heal]`，出现在 `start.log` 里。
冷却 5 分钟：token 真过期时反复捞只会刷日志，捞一次失败就把界面切回"需要重新登录"。

触发点有两类，都是"认出 AUTH 就捞"：

- **后台采集**（`_evt_worker` 的实时属性、12 分钟一次的 `device_list`）
- **前台请求**（`/api/live`、`/api/getprops`、`/api/setprop`、`/api/action`）

前台这条很关键：`/api/live` 是 4 秒一次的热路径，如果它撞上 AUTH 却没人管，
用户就会一直看着"设备不刷新"，直到自己重启程序。

另外 `/api/live` 失败时，**手上有上一轮数据就先顶上**（返回 `stale: true` +
错误说明），不再因为一次抖动把整页设备打灰。

### 传输层：连接复用（mihttp.py）

miservice 自带的 `biohttp` 是 **urllib + 每次 `build_opener()`**，每个请求都重做
一遍 TCP + TLS 握手。实测到 `api.io.mi.com`（2026-10-26，本机）：

| 阶段 | 每次新建 | 复用 |
|---|---|---|
| DNS（OS 缓存命中） | 1.1 ms | — |
| TCP 握手 | 52.5 ms | — |
| TLS 握手（TLS 1.2，2 RTT） | 122.3 ms | — |
| 请求往返 | 51.6 ms | 51.9 ms |
| **合计** | **227.5 ms** | **51.9 ms** |

**单次省 175 ms（-77%）**。改完之后真机复测同一接口：首请求 277 ms，
之后稳定 55 ms，6 个请求只建 1 条连接。

**为什么不直接改 biohttp**：登录走 `account.xiaomi.com`，它依赖 biohttp 的
重定向 + Set-Cookie 捕获（`serviceToken` 就在那条链路里）。所以按主机分流：

| 主机 | 走哪条 | 理由 |
|---|---|---|
| `account.xiaomi.com` | 原样 biohttp | 登录是全程序最不能出意外的一段，那 0.2 秒不值得换风险 |
| `api.io.mi.com` | `mihttp.PooledSession` | 99% 的请求都在这儿 |

复用的三条安全保证（都在 `mihttp.py` 顶部注释里）：

1. **只复用读干净的连接** —— 每次 `read()` 到结尾，没读完绝不还池（串包是最脏的失败模式）
2. **复用前体检** —— 空闲 > 25 秒、或 socket 已可读（服务端发了 EOF）就丢弃重建
3. **出错即弃** —— 连接层异常一律扔掉再抛，**传输层不擅自重放**，
   重不重试交给 netguard 的策略（否则 `action` 可能被执行两次）

**怎么看有没有生效**：`/api/status` 的 `http` 字段。
`requests` 涨而 `reconnects` 不跟着涨 = 复用在工作；两者接近 1:1 = 每次都在重连。

**逃生口**：设环境变量 `MIHOME_HTTP_POOL=0` 启动，整段退回原实现，
不用改代码。出怪问题时第一件事就是加这个变量重启，看是不是传输层的锅。

### 一条仍然没做的

`device_list` 冷启动那 20~30 秒**不是**传输层造成的：它只发 1 个请求，
227 ms 占 25 秒的 0.9%，大头在米家云那一侧。想再快只能从"少调它"入手
（现在 12 分钟一次 + 有缓存兜底，已经压得比较狠了）。
